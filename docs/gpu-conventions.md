# GPU conventions: Mesa's device code on FerrionOS

How each convention that Mesa's Venus driver relies on in Linux maps to FerrionOS: node names, enumeration, request numbers and sizes, nested pointers, `mmap` offsets, `poll`, sync objects, sync files, buffer descriptors, shared memory and the clock behind deadlines. The calls themselves, one entry each, are in the [needs ledger](gpu-needs-ledger.md). Since the integration of slices GP4 to GP7, a program with the render name draws on the host's GPU through Venus and through Zink on Venus; everything else still draws on the CPU, and the display scheme shows dumb buffers only. The conventions of rows marked GP3, GP4 (but for enumeration and device numbers), GP6 (page flips) and GP7 (sync objects and sync files) are built, as ADRs 0028 to 0034 record; the rest is still the rule that the driver, relibc and libdrm follow when the slice named builds it.

Slice names are those of the maintainer's GPU plan: GP3 a render handle and a Venus context; GP4 first pixels, with blobs, the host-visible window, submissions and fences; GP6 a rendered buffer on the screen; GP7 buffers and fences between processes; GP9 clients on screen; GP11 a Linux session; GP12 grants, quotas and hostile requests.

## The `virtgpu` module and the layout check

FerrionOS's [`ferrion-redox-ioctl-virtgpu.patch`](../recipes/core/relibc/ferrion-redox-ioctl-virtgpu.patch) adds a `virtgpu` module to relibc's crate `redox-ioctl`, the crate in which relibc's DRM translation and `base`'s graphics drivers share their wire types. It holds every number, flag and structure of Linux v7.3's `virtgpu_drm.h`, with that header's MIT notice, DRM's own close request from `drm.h`, and the payloads the driver will receive for the eight requests Venus makes that relibc does not carry yet (map, submission, get-parameter, resource info, get-capset, blob create, context-init, close), with unit tests that send them both ways. It gives `define_ioctl_data!` the array directions described above, and every payload of the macro, in both modules, a `LAYOUT` constant that lists its fixed fields with their offsets and sizes, then its arrays with their element's size and alignment and their direction. The `drm` module's wire format does not change. [`ferrion-redox-ioctl-views.patch`](../recipes/core/relibc/ferrion-redox-ioctl-views.patch) then gives a payload's view `<array>_mut()`, which writes an array in place and keeps its count. Nothing calls the `virtgpu` module yet. `base` took `redox-ioctl` from upstream's repository by URL (its `Cargo.toml` line 105); FerrionOS's [`ferrion-redox-ioctl-path.patch`](../recipes/core/base/ferrion-redox-ioctl-path.patch) turns on the path override the manifest carried as a comment (line 135), so the display drivers and relibc compile the same crate with both patches. relibc's source must then be fetched before `base` is cooked, which the prefix's sysroot does, and a change to relibc's `redox-ioctl` patches needs `base` cooked again.

`python3 scripts/virtgpu-layout-check.py` compiles the header, a copy of Linux v7.3's in `scripts/virtgpu-layout/linux/` checked by its sha256, with the close request's structure and number from the `drm.h` beside it, in C, and the module in Rust with the toolchain relibc pins. It compares the size and alignment of every structure; the offset, size and type of every field; every number the headers define, the twelve request numbers among them; and, for every payload, its function number against the header's request, the type, number and size field of the module's own request number against the module's structure, its fixed part against the header's structure without the array pointers, each array's pointer, count and element, each array's direction against what Linux's driver does with it, and that its arrays stay aligned. It fails on an empty payload list and on a structure or a function number listed twice. Then it runs the crate's own tests. On 2026-11-21 it passed: 15 structures, 57 numbers, 12 requests and 8 payloads, 218 items. It failed, as it should, on a module with two fields swapped, on one with the 48-byte blob-create structure, on one with `fence_fd` unsigned, on one whose submission sends its command before its sync objects, on one that copies the command back, whose test then faults on a command in read-only memory, on one that sends blob create's command both ways, on one that lists a payload twice, on one with no payloads, and on one whose close request is numbered read-write. `--header` compares another copy of the header, with the `drm.h` beside it:

- Mesa 26.3.1's own copy, `include/drm-uapi/virtgpu_drm.h`, passes with 217 items: it lacks `VIRTGPU_PARAM_BLOB_ALIGNMENT`, which `vn_renderer_virtgpu.c:37-40` defines for itself. Mesa gives the same number 9 to a parameter of its own, `VIRTGPU_PARAM_GUEST_VRAM`, and asks for it only on a device without a host-visible window (`30-33`, `1065-1077`).
- libdrm 2.4.125's copy, `include/drm/virtgpu_drm.h`, fails, as it should: it is older, with `stride` where Linux has `blob_mem` in `drm_virtgpu_resource_info`, and with no blob or context-init request. Mesa does not read it, but a program that takes its include path from libdrm's `pkg-config` file and includes `virtgpu_drm.h` would.
