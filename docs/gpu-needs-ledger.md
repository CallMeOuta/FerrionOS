# GPU needs ledger: the calls of Mesa's Venus driver

One entry per call that Mesa's Venus driver makes on a GPU device, in `src/virtio/vulkan/vn_renderer_virtgpu.c` and in the libdrm, libsync and sync-object code it reaches, in the order Venus makes them. Each entry gives what Linux does, what FerrionOS answers today, what Venus does with that answer, what FerrionOS needs, and the slice that adds it. The conventions behind the entries, and the sources, commits and citation form, are in [the conventions table](gpu-conventions.md): `file:A-B` is lines A to B at the commit named there, and a bare line number is in `vn_renderer_virtgpu.c` at Mesa 26.3.1.

Every entry is marked **expected**: read in the source, not run on FerrionOS, because no FerrionOS image has run Venus yet. An entry becomes **observed** when a check has seen it, and the mark then names the check: GP3's `gpu-context` and GP4's `vk-exact` are the first to do so.

## Counts

The renderer file names ten DRM requests: seven of virtio-gpu's own (map, submission, get-parameter, resource info, get-capset, blob create, context-init), close, and buffer export and import. libdrm adds the version request, made twice, and the capability request. If the capability says the device has timeline sync objects, Venus adds eight sync-object requests, and a ninth when it is told not to use timelines. Outside the DRM file it calls `ioctl` once on a buffer descriptor (entry 32) and once on sync files (entry 34), and `open`, `stat`, `mmap`, `munmap`, `dup`, `poll` and `close`.

## Venus's start-up, in order

1. `vkCreateInstance` creates the renderer: it lists the devices (entry 1), opens the first that passes (entries 2 to 5), asks the parameters in this order: `3D_FEATURES`, `CAPSET_QUERY_FIX`, `RESOURCE_BLOB`, `CONTEXT_INIT`, `HOST_VISIBLE`, then `BLOB_ALIGNMENT`, then the optional `CROSS_DEVICE` (entries 6 to 9, `1039-1098`), reads the Venus capset (entry 10) and initializes the context with capset 4, 64 rings and ring mask 0 (entry 11). Then it asks the capability of entry 12.
2. It then creates the instance ring's shared memory (entries 13 and 14) and talks to the host's renderer over it. The capset's `wire_format_version` must equal the guest's own exactly, and the host's Vulkan XML version, cut down to the guest's, must be at least Venus's minimum (`vn_instance.c:156-190`).
3. **A failed device is no failed call.** When the renderer cannot be created, `vkCreateInstance` still answers `VK_SUCCESS`, with no renderer (`vn_instance.c:303-307`), and `vkEnumeratePhysicalDevices` then reports zero devices (`vn_physical_device.c:1837-1840`). A probe checks the number of devices, not the result of `vkCreateInstance`.
4. Venus's start-up messages, `VN_DEBUG=init`, go through `mesa_log_v` at the debug level (`vn_common.c:93-98`), which a release build of Mesa prints only with `MESA_LOG_LEVEL=debug` (`src/util/log.h:50-52`, `log.c:134-135`).

## What Mesa itself needs on FerrionOS

These are changes to Mesa's own source, not to the device, and GP4's Mesa patches carry them:

- `meson.build:160` lists the systems with DRM in `system_has_kms_drm`, and FerrionOS's `redox` is not among them. Without it `vn_renderer_virtgpu.c` is not built at all (`src/virtio/vulkan/meson.build:131-136`), and Venus has only its test transport.
- `vn_gettid()` falls through to `syscall(SYS_gettid)` on systems other than Android, FreeBSD and Windows (`vn_common.h:642-654`). relibc has no `syscall()` on FerrionOS (it builds `unistd/syscall.rs` for Linux only, relibc `src/header/unistd/mod.rs:61-62`) and no `SYS_gettid`, and it exports no `gettid()` either: its thread number is internal (`src/platform/redox/mod.rs:801-806`). Venus uses the number to tell the thread that presents from the others (`vn_wsi.c:406`, `454`, `487`) and in its watchdog (`vn_common.c:129-138`). So relibc exports `gettid()` and Mesa's `vn_gettid()` calls it on FerrionOS.
- `getpriority(PRIO_PROCESS, 0)` for a thread's ring priority, asked only when the host's Venus protocol is version 2 or newer, with -1 and an error read as no priority (`vn_ring.c:338-348`). relibc implements it (relibc `src/header/sys_resource/mod.rs:202`, `src/platform/redox/mod.rs:669-677`), so nothing more is needed.

## Venus reaches its first pixels without sync objects

When the capability request of entry 12 does not answer 1, Venus keeps its sync objects inside the process (`976-993`, `vn_renderer_sim_syncobj.c:309-322`): each holds the sync file a submission returned, and waits are a `poll` on it (entries 19 to 21). So GP4 needs fence descriptors that can be duplicated, polled and closed, and no sync-object request. The other path, the one Linux 6.6 and later give Venus, needs entries 22 to 29 all at once, and the capability answers 1 only when they all work: that is GP7.

## What each slice takes

- **GP3**: entries 2, 3, 4, 6, 9, 10, 11, 17 and 35. With them, a probe can open a render handle and a Venus context; Venus itself does not start yet, because of entries 1 and 7.
- **GP4**: entries 1, 5, 7, 8, 12 (answering 0), 13, 14, 15, 16 for created blobs, 18 to 21 and 33. With them, Venus starts and draws off-screen on the simulated sync objects.
- **GP6**: entry 33 again, for frames on screen.
- **GP7**: entries 12 (answering 1), 16 for imports, 22 to 32 and 34.
