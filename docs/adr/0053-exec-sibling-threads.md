# Ending sibling threads on exec

Status: accepted

## Context

Exec ends every other thread of the process before the new program runs. On FerrionOS, `exec` runs in userspace (`relibc`'s `redox-rt::proc::fexec_impl`) and `procmgr` (`base`'s `bootstrap/src/procmgr.rs`) owns every thread's kernel status handle and thread-death event subscription, while `libredox` continues to come from crates.io as an unmodified upstream dependency.

## Decision

- **FerrionOS-owned `procmgr` thread-handle verb range (`0x4645_xxxx`):** FerrionOS reserves thread-handle call verb numbers in the `0x4645_xxxx` namespace, outside upstream's dense `ThreadCall` discriminants starting at `0`, so `libredox` stays unmodified from crates.io without vendoring or `[patch.crates-io]` changes. `THREAD_CALL_TERMINATE_SIBLINGS = 0x4645_0001` is matched on `Handle::Thread` in `procmgr` before `ThreadCall::try_from_raw` and sent raw by `redox-rt`. The two constants must match across `components/relibc` and `components/base`, and can merge into one shared definition in-tree as a follow-up.
- **`procmgr` sibling teardown and unstarted-child discard (`components/base/bootstrap/src/procmgr.rs`):** On `0x4645_0001` over `Handle::Thread`, `procmgr` treats the handle's thread as the survivor (not necessarily the calling thread: a thread invoking the verb on a sibling's handle within the same process ends every thread except that sibling, itself included; `relibc` only passes its own thread handle). It rejects callers whose PID does not match the thread's process (`EPERM`), rejects processes with more than `MAX_EXEC_SIBLINGS` (`1024`) threads before sending any kill (`E2BIG`), and returns `Ok(0)` immediately when only the surviving thread exists and the process has no tracked unstarted children. When only the surviving thread exists and tracked children remain, it calls `discard_unstarted_children` directly, returning `Ok(0)` without inserting pending state if none needed teardown, or setting sibling teardown active and entering `PendingState::AwaitingSiblingsTermination` if any unstarted child was killed. When multiple threads exist, it marks sibling teardown active (refusing `new-thread` and `fork` with `EAGAIN`), writes `ContextVerb::ForceKill` to every other thread's status handle, and waits asynchronously in `PendingState::AwaitingSiblingsTermination` driven by kernel thread-death events until only the surviving thread remains. Each child created by `fork` or `posix_spawn` is appended to the parent's `unstarted_children` queue (bounded by `MAX_EXEC_UNSTARTED_CHILDREN = 1024`). On each `fork`, `procmgr` inspects up to `MAX_FORK_PRUNE_STEPS` (`2`) entries at the front of the queue (and scans the full queue if at the cap, returning `EAGAIN` if still full), dropping an entry only on positive evidence that the child has started or ended (gone, reparented, exiting/exited, multi-threaded, or thread status `Runnable`, `Blocked`, `Dead`, `ForceKilled`, or `UnhandledExcp`) and rotating `NotYetStarted`, `Other`, `Stopped`, stopped processes, or read errors to the back so an in-flight child paused for address-space or file-table install is never dropped prematurely. Once every sibling has ended at `exec`, or once `threads` is empty during process exit in `PendingState::AwaitingThreadsTermination` (before reparenting to `init`), `procmgr` checks each tracked child's kernel context status and discards every child still in `ContextStatus::NotYetStarted` by marking it `aborted_before_start` and writing `ContextVerb::ForceKill` to its status handle. Both waits stay pending until each discarded child exits and is reaped directly without sending `SIGCHLD` or recording a `waitpid` status (while waking any pending `waitpid` waiters to re-evaluate), so no never-started child survives `exec` or reaches `init` on exit. Neither wait has a timer and both are cancelled by process exit, `SIGKILL`, or request cancellation ([ADR 0024](0024-tigerstyle.md)).
- **`relibc` lock order and fail-closed exec (`components/relibc/redox-rt/src/proc.rs`, `components/relibc/src/platform/redox/mod.rs`):** `Sys::execve` and `Sys::fexecve` register `ForkAllocHooks` alongside `Sys::fork`. In `fexec_impl` (`same_process == true`), after all fallible image, interpreter, stack, and auxiliary-vector setup succeeds and `tmp_disable_signals()` is active, `fexec_impl` acquires the five [ADR 0049](0049-fork-file-table-and-grants.md) locks in order (`DYNAMIC_PROC_INFO -> FILETABLE.inner -> FILETABLE.fd -> ALLOCATOR -> SIGACTIONS_LOCK`), sends `0x4645_0001` on `thread_fd` (retrying `EINTR` up to `EXEC_SIBLINGS_MAX_RETRIES = 16`, failing closed via `posix_exit(127)` on any error or exhausted retries), and releases all five locks once `procmgr` replies that every sibling has ended. The existing close-on-exec and handle-cleanup tail ([ADR 0050](0050-exec-runtime-handles.md)) then runs with no other thread able to hold those locks, and `deactivate_tcb(thread_fd)` also fails closed via `posix_exit(127)` so `exec` cannot return an error after siblings have already been ended.

## Consequences

- `relibc` and `base` ship together: because `relibc` fails closed on `EINVAL` when `procmgr` does not recognize `0x4645_0001`, installing a new `relibc` (`make p.relibc` alone) into an older image without the matching `base` breaks every `exec`.
- Statically linked programs that call `exec` directly from a multithreaded process pick up this rule only after being recooked against the updated `relibc`.
- Single-threaded `exec` takes one additional fast-path `procmgr` round trip on `thread_fd` (returning immediately when `threads.len() == 1` and `unstarted_children` is empty, or directly after pruning started entries via `discard_unstarted_children` without entering pending state); amortized fork-time pruning keeps `unstarted_children` bounded to recently forked children instead of all live children, and `posix_spawn` does not take the `same_process` path.
- A sibling killed mid-`fork` during `exec` or process exit no longer leaves an unstopped never-started child process holding inherited descriptors or blocking `waitpid(-1)`; a process with `MAX_EXEC_UNSTARTED_CHILDREN` (`1024`) live never-started children receives `EAGAIN` from `fork`.
- A never-started child stopped by `SIGSTOP` or `SIGTSTP` before it starts no longer reads `NotYetStarted`, so discard misses it until `.scratch/kernel/issues/28-stop-on-not-yet-started-context.md` is fixed.
- A process with more than `1024` threads cannot `exec` (exits `127`).
- The allocator hook is installed by `relibc`'s `Sys::execve` and `Sys::fexecve`, so an `exec` through `redox-rt` without `relibc`'s platform layer (such as `bootstrap`) runs without the allocator lock, which is safe only because it is single-threaded.
- Any future FerrionOS-owned `procmgr` thread-handle or kernel `ContextHandle::Attr` verb takes the next value in `0x4645_xxxx` and is recorded alongside `0x4645_0001`.
- `ATTR_CALL_SET_RUID = 0x4645_0002` is handled on `ContextHandle::Attr` (`components/kernel/src/scheme/proc.rs`, behind `ContextHandle::Authority`) and sent by `procmgr` (`components/base/bootstrap/src/procmgr.rs`) right after writing `ProcSchemeAttrs` so kernel `Context.ruid` stays synced without changing `ProcSchemeAttrs`.
