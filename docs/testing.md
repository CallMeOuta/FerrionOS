# Checks

What can be checked in this repository, cheapest first: what each check proves and what it needs. Climb only as far as the change requires, and name in your report the highest rung you reached and what you could not run.

## The ladder

| Rung | Command | Proves | Needs |
|---|---|---|---|
| 1. Syntax | `bash -n <script>` for shell, `python3 -c 'import sys,tomllib; [tomllib.load(open(f,"rb")) for f in sys.argv[1:]]' <file.toml>` for TOML, `make -n <target>` for makefiles, `python3 scripts/security-audit.py` after a change to accounts, a recipe's `[source]` or a download, `python3 scripts/naming-check.py` after a change to any text, `python3 scripts/no-x11-check.py` after a change to a recipe's dependencies or a config's packages, `python3 scripts/virtgpu-layout-check.py` after a change to relibc's `redox-ioctl` or to `scripts/virtgpu-layout/`, and with `--header` on Mesa's own `include/drm-uapi/virtgpu_drm.h` when Mesa's pin moves | The file parses; for make, which commands a target would run; for the audit, that the change adds no security finding beyond `scripts/security-audit.baseline.jsonl` (exit code 1 when it does, the script's header lists the checks); for the naming check, that no new line names the upstream project outside the exceptions of `AGENTS.md` "Naming" and `scripts/naming-check.baseline.jsonl`; for the X11 check, that no recipe depends on an X11 package and no config installs one; for the layout check, that every structure size and alignment, field offset and number of Linux's `virtgpu_drm.h`, the request numbers among them, equals that of `redox-ioctl`'s `virtgpu` module, that each payload the driver receives is the header's structure without its pointers, with its arrays aligned and each travelling the way Linux's driver moves it, and that the crate's own tests pass (exit code 1 on a difference, 2 when it cannot run). | Nothing; the layout check needs a C compiler, the Rust toolchain relibc pins and relibc's source (`make f.relibc`). |

| 3. Graph | `make rt.<recipe>`, `make repo-tree`, `make image-tree` | The recipe matches the schema, and every dependency and every package of the config names an existing recipe. | The cookbook built (`build/fstools.tag`). |
| 4. Fetch | `make f.<recipe>` | The source URL answers, the `blake3` matches and the patches apply. | Network. |
| 5. Cook | `make r.<recipe>` | The recipe builds and packages for one architecture. | The container or the native tools, the prefix, and its build dependencies cooked. |
| 6. Image | `make image`, `make qemu`, `scripts/vm-test.py boot` | The config assembles into an image, and the image boots; with the script, that the boot stays quiet and reaches the login (see [`agents/skills/images-and-qemu.md`](../agents/skills/images-and-qemu.md)). | Every package of the config cooked. |

`make -n` still parses every makefile. With `PODMAN_BUILD=0`, which image targets also pass to a nested make, that parse calls `rustc`, and rustup then installs the pinned toolchain when it is missing.

## Spending a run well

- A cook or an image build is the most expensive action here. A first `make all` builds the container, the toolchain prefix and every package of the config, and the book's [Developer FAQ](../book/src/developer-faq.md) asks for "50GB of storage space or more". Start one when the task needs its result, once, at the end.
- Cook with `CI=1 COOKBOOK_LOGS=true` in the environment. `CI` turns off the cookbook's terminal interface, which needs a terminal and waits at a prompt when a recipe fails. `COOKBOOK_LOGS=true` keeps each recipe's output in `build/logs/<target>/<recipe>.log`.
- A Podman build runs `podman run --interactive --tty` (`PODMAN_OPTIONS` in `mk/podman.mk`), and Podman's [manual](https://docs.podman.io/en/latest/markdown/podman-run.1.html) says of `--tty`: "This option is only used when run interactively in a terminal." Start a Podman-mode make from a terminal or a pseudo-terminal.
- Write the whole output of a long command to a log file and read it from there. What `grep`, `head` or `tail` drop from a pipe costs a whole run to get back.
- Run a check again only after changing something it covers. A cook is incremental: an unchanged recipe reports `cached`.
- A failure in a recipe or test you did not touch is usually pre-existing. Git recipes without `rev` follow upstream's branch head, so any fetch can bring in a broken commit; `target/<target>/source_info.toml` in the recipe directory records the revision that was built. Check [`platform-state.md`](platform-state.md) for a known limit, report the failure with its log, and keep it out of your change.

## Suites that run inside the OS

Each is a filesystem config whose init script starts the suite and ends with `shutdown`, so QEMU exits when the run is over:

- `config/acid.toml`: `acid-runner`.
- `config/auto-test.toml`: `acid-runner`, relibc's tests and `os-test-runner`.
- `config/os-test.toml`: `os-test-runner`.
- `config/sys-build.toml`: cooks the system on FerrionOS itself.

`make ci-os-test` in `mk/ci.mk` is the worked example: it boots `CONFIG_NAME=os-test` with `gpu=no`, then mounts the image and copies the results to `build/os-test/<arch>/`. [`agents/skills/images-and-qemu.md`](../agents/skills/images-and-qemu.md) has the procedure for a suite of your own.

`scripts/vm-test.py boot-gc-generation` boots a temporary copy with its RedoxFS header advanced to the next allocator-GC threshold and requires the graphical login. Prepare its host fixture with `cargo +nightly build --manifest-path recipes/core/redoxfs/source/Cargo.toml --target-dir build/fsgc-host --example boot_gc_generation`, then `install -m755 build/fsgc-host/debug/examples/boot_gc_generation build/fstools/bin/`. The host regression is `cargo +nightly test --manifest-path recipes/core/redoxfs/source/Cargo.toml --test read_only_transaction`: unchanged transactions issue no writes on a disk that refuses them, and the next writing transaction still reclaims the allocator log. The bootloader consumes the recipe-patched RedoxFS source, not a separate registry version; after changing it, cook `redoxfs`, `bootloader` and `base`, then rebuild the image so its EFI partition contains the new bootloader.

The x86_64 desktop's command and name-resolution regressions run with `python3 scripts/vm-test.py cli-tools resolver --arch x86_64 --config desktop --timeout 120`. `cli-tools` checks GNU sed, GNU awk and extrautils' gzip tar round-trip with `-C`; it does not cover process arguments. `resolver` checks hosts-file names as an ordinary user and captures DHCP and DNS packets to compare the queried server with the advertised server. Both need an image rebuilt with the recipe patches; installing a new libc alone does not update programs that linked it statically.

The package commands run with `python3 scripts/vm-test.py ferrion-cli update-today --arch x86_64 --config desktop --timeout 120`. `ferrion-cli` reaches no outside server: it checks that `ferrion search` refuses with exit code 6 while the image names no package source, then adds a source served from the host for the check, holding one package of this build's `repo/` (`gnu-make`, which the desktop image lacks) signed by the build's key, and installs, runs and removes it; `gnu-make` must be cooked. `update-today` runs `ferrion update` and `pkg update` as root with the network up and passes when nothing was fetched: no TCP connection or DNS question in a capture of `net0`, the hashes of `usr/lib/boot/kernel` and `usr/lib/boot/initfs` unchanged, and the next start reaching the login. That a replaced kernel or initfs is refused at the next start is `scripts/secure-boot-test.sh`'s tamper cases.

The GTK display check is `python3 scripts/vm-test.py gtk-window --config firefox-window --timeout 120`, after building `config/x86_64/firefox-window.toml` in a lane worktree. It uses the already cooked Firefox package and adds `gtk-window-probe`: a native GTK3 window with a fixed blue background and white label, closed by a timer. The check logs in graphically, starts the probe from the serial shell with `GDK_BACKEND=orbital ORBITAL_DISPLAY=/scheme/orbital`, checks the screenshot's background and label pixels, then requires a normal exit and removal of the window. It saves `gtk-window.png`, `gtk-window-closed.png`, pixel counts and the serial log under the run directory. This proves GTK's Orbital backend, not Firefox's display support: Firefox's `cairo-gtk3-wayland-only` toolkit rejects an Orbital GDK display and needs a running Wayland compositor.

The corresponding Wayland check is `python3 scripts/vm-test.py gtk-window-wayland --config firefox-wayland --timeout 120`. That config derives from `wayland.toml`, runs cosmic-comp nested inside Orbital, and records the compositor's actual `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR` in `/tmp/gtk-window-session`. The check logs in as root to match this development compositor session, sources that environment and runs the same probe with `GDK_BACKEND=wayland`. To try Firefox on that display, source the same file from Bash, create `/tmp/firefox-window-profile`, then run `GDK_BACKEND=wayland MOZ_ENABLE_WAYLAND=1 firefox --no-remote --profile /tmp/firefox-window-profile about:blank` without `MOZ_HEADLESS`. GTK prefers Orbital when `ORBITAL_DISPLAY` is inherited, so selecting its Wayland backend explicitly matters even though Firefox itself is a Wayland-only build. The GTK probe does not prove that Firefox finishes startup or renders a page.

The GPU host reference runs with `nice -n 10 python3 scripts/gpu-reference-guest.py --vk-driver /usr/share/vulkan/icd.d/intel_icd.json --render-node /dev/dri/renderD128` (choose the host's actual ICD and render node; `VK_DRIVER_FILES` also supplies the ICD). It needs Python 3.11+, `bsdtar`, `zstd`, x86_64 Linux with accessible KVM, QEMU with Venus and `egl-headless`, and working host graphics drivers. It needs no FerrionOS build or host root: checksum-pinned Fedora RPMs become an initramfs, whose programs execute only inside an offline, windowless QEMU guest with `-snapshot`. The host reads archive data without running package scriptlets. First use downloads exact signed builds from Fedora's Koji archive; `--fetch-only` populates the cache, and subsequent runs check every cached hash. The script carries the build paths, SHA-256 values and release-key fingerprints used to authenticate the RPM headers and payloads when establishing the pins. `vulkaninfo`, `eglinfo`, and the host package manager add runtime and package versions when installed; an unusable host or a driver mismatch is `BLOCKED` (exit 2).

The default variant is `fedora45`, containing Fedora 45 release and updates packages. `--variant mesa263` selects the same base with rawhide Mesa matching the target release and its minimal runtime dependencies; `--variant all` writes both in one record. Both retain Fedora 45's kernel. The record labels Mesa, glibc and LLVM versions and lists every input hash. Each invocation boots the three device lines twice by default and compares scene hashes, differing-pixel counts, and the complete Venus capset bytes. It writes one `build/gpu-reference/run-*/result.json`, with per-boot serial logs and `virtio_gpu_*` QEMU traces beside it. For a capset comparison, select the matching variant and the same host GPU and QEMU device line, then read `variants[].runs[].guest.venus_capset` (`bytes_hex`, byte count and SHA-256).

`PASS` checks virgl, the CPU reference, Zink on Venus, and host submission evidence. Native contexts are recorded separately and do not gate this Venus reference: the stock Fedora packages leave Mesa's `intel-virtio-experimental` option at its default `false`, so capset 6 can be offered by the host while the guest's Intel native driver remains unavailable. The record preserves the native Vulkan and OpenGL attempts and links the package-build evidence. This is a Linux reference for the host, not proof of FerrionOS GPU support. `python3 scripts/gpu-reference/test_reference.py` checks checksum rejection, host floors, and repeatability without downloading or booting.

`scripts/vm-test.py audio-apps` exercises the audio service through its public scheme and the Rust client in `recipes/core/ferrion-audio/crate`: legacy PCM playback, two program identities with independent gains, readable `volume`, the CLI's JSON commands, and 10,000 stream opens and closes. It boots with its own HDA device and WAV backend, as `audio-baseline` and `audio-ring` do. The first boot uses the old PCM interface too, so a missing probe is not accepted as the expected red result. Build `audio-probe`, `ferrion-audiod` and `ferrion-cli` before the green run.

The AU2 stream interface is stereo float32 little-endian at 44,100 Hz, opened at `/scheme/audio/stream`; the scheme root remains signed 16-bit stereo at the same rate. A stream's relative `gain` handle takes amplitude decibels, or `mute`. Root can create `/scheme/audio/factory/<identity>/<session>` and pass its descriptor to a client, which opens `stream` relative to it: the identity is attached to that factory, not supplied by the client. Until launchers pass factories, named stream opens use the kernel caller's process ID and user ID, not a claimed executable identity. Root-only `program/<identity>/gain`, `session/<session>/gain`, `apps`, `status` and `stats` expose controls and diagnostics. Program and session gains persist in the running server, not across restarts. The existing `volume` handle remains available to existing clients, with its original 0–100 cube law. Capture, shared client rings and the launcher integration are not part of this interface yet.

`ferrion audio status`, `apps` and `volume` each accept `--json`. `volume --app ID 50 --yes` sets half linear amplitude for that program; `volume 50 --yes` retains the legacy master curve. The service starts in place of `audiod` through the config's replacement `20_audiod.service`, serves the same `audio` scheme and retains only `memory` and `rand` in its namespace after opening the output device.

The first reference baseline used Debian 13: Mesa 25.0.7 reported Venus API 1.3.269, conformance 1.3.0.0 and 113 Intel device extensions; a Mesa 26.2.6 overlay reported API 1.4.334, conformance 1.4.0.0 and 178 extensions. Both produced scene hash `47972063c7a47bfb` with zero differing pixels and the same 160-byte Venus capset SHA-256, `11069f17d3858d6b725a3b2b2b810fafc6ae6529ccdedf45bab62acdcb342609`. Its kernel 6.12 could not use Intel native contexts. These are historical host-specific measurements, not expected capability counts for every host. The reference now uses Fedora; the separate Linux compatibility layer's Debian pin is unchanged.

## What upstream's CI ran

Upstream gates its merge requests on a `.gitlab-ci.yml` that is not part of this checkout, and FerrionOS has no CI of its own yet. The upstream jobs, read on 2026-11-20:

- `cargo fmt -- --check`
- `RUSTFLAGS="-Dwarnings" cargo test --locked`
- `make CONFIG_NAME=ci SKIP_CHECK_TOOLS=1 repo-tree ARCH=<arch>` and the same for `CONFIG_NAME=demo`, with `PODMAN_BUILD=0`, for each supported architecture: `x86_64`, `aarch64` and `riscv64gc`
- `./scripts/fetch-changed.sh`, which fetches every recipe whose `recipe.toml` differs from `origin/master` and so needs a git checkout
- `make desktop` with `REPO_BINARY=1` and `FSTOOLS_NO_MOUNT=1`, an image assembled from prebuilt packages. Here that job also needs `VERIFIED_BOOT=0`: verified-boot signing mounts the image through FUSE, which `FSTOOLS_NO_MOUNT=1` leaves out
