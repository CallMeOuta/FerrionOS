# Checks

What can be checked in this repository, cheapest first: what each check proves and what it needs. Climb only as far as the change requires, and name in your report the highest rung you reached and what you could not run.

Agent-written changes require a VM check, a differential comparison with an independent reference, or a deterministic simulation with injected faults, red before the fix and green after it ([ADR 0025](adr/0025-tests-without-unit-tests.md)). Upstream tests stay; agents do not add unit tests.

## The ladder

| Rung | Command | Proves | Needs |
|---|---|---|---|
| 1. Syntax | `bash -n <script>` for shell, `python3 -c 'import sys,tomllib; [tomllib.load(open(f,"rb")) for f in sys.argv[1:]]' <file.toml>` for TOML, `make -n <target>` for makefiles, `python3 scripts/security-audit.py` after a change to accounts, a recipe's `[source]` or a download, `python3 scripts/naming-check.py` after a change to any text, `python3 scripts/no-x11-check.py` after a change to a recipe's dependencies or a config's packages, `python3 scripts/comment-check.py` after a change to any code, `python3 scripts/virtgpu-layout-check.py` after a change to relibc's `redox-ioctl` or to `scripts/virtgpu-layout/`, and with `--header` on Mesa's own `include/drm-uapi/virtgpu_drm.h` when Mesa's pin moves | The file parses; for make, which commands a target would run; for the audit, that the change adds no security finding beyond `scripts/security-audit.baseline.jsonl` (exit code 1 when it does, the script's header lists the checks); for the naming check, that no new line names the upstream project outside the exceptions of `AGENTS.md` "Naming" and `scripts/naming-check.baseline.jsonl`; for the X11 check, that no recipe depends on an X11 package and no config installs one; for the comment check, that no tracked file has more comment lines than `scripts/comment-check.baseline.json` allows, beyond the kinds `scripts/comment-check.config.json` keeps (exit code 1, printing each comment of a file over its count); for the layout check, that every structure size and alignment, field offset and number of Linux's `virtgpu_drm.h`, the request numbers among them, equals that of `redox-ioctl`'s `virtgpu` module, that each payload the driver receives is the header's structure without its pointers, with its arrays aligned and each travelling the way Linux's driver moves it (exit code 1 on a difference, 2 when it cannot run). | Nothing; the layout check needs a C compiler, the Rust toolchain relibc pins and relibc's source (`make f.relibc`). |

## Spending a run well

- A cook or an image build is the most expensive action here. A first `make all` builds the container, the toolchain prefix and every package of the config, and the book's [Developer FAQ](../book/src/developer-faq.md) asks for "50GB of storage space or more". Start one when the task needs its result, once, at the end.
- Cook with `CI=1 COOKBOOK_LOGS=true` in the environment. `CI` turns off the cookbook's terminal interface, which needs a terminal and waits at a prompt when a recipe fails. `COOKBOOK_LOGS=true` keeps each recipe's output in `build/logs/<target>/<recipe>.log`.
- A Podman build runs `podman run --interactive --tty` (`PODMAN_OPTIONS` in `mk/podman.mk`), and Podman's [manual](https://docs.podman.io/en/latest/markdown/podman-run.1.html) says of `--tty`: "This option is only used when run interactively in a terminal." Start a Podman-mode make from a terminal or a pseudo-terminal.
- Write the whole output of a long command to a log file and read it from there. What `grep`, `head` or `tail` drop from a pipe costs a whole run to get back.
- Run a check again only after changing something it covers. A cook is incremental: an unchanged recipe reports `cached`.
- A failure in a recipe or test you did not touch is usually pre-existing. Git recipes without `rev` follow upstream's branch head, so any fetch can bring in a broken commit; `target/<target>/source_info.toml` in the recipe directory records the revision that was built. Check [`platform-state.md`](platform-state.md) for a known limit, report the failure with its log, and keep it out of your change.

## Suites that run inside the OS

Each is a filesystem config whose init script starts the suite and ends with `shutdown`, so QEMU exits when the run is over:

- `config/acid.toml`: `acid-runner`.
- `config/auto-test.toml`: `acid-runner`, relibc's tests and `os-test-runner`.
- `config/os-test.toml`: `os-test-runner`.
- `config/sys-build.toml`: cooks the system on FerrionOS itself.

`make ci-os-test` in `mk/ci.mk` is the worked example: it boots `CONFIG_NAME=os-test` with `gpu=no`, then mounts the image and copies the results to `build/os-test/<arch>/`. [`agents/skills/images-and-qemu.md`](../agents/skills/images-and-qemu.md) has the procedure for a suite of your own.

`scripts/vm-test.py boot-gc-generation` boots a temporary copy with its RedoxFS header advanced to the next allocator-GC threshold and requires the graphical login. Prepare its host fixture with `cargo +nightly build --manifest-path recipes/core/redoxfs/source/Cargo.toml --target-dir build/fsgc-host --example boot_gc_generation`, then `install -m755 build/fsgc-host/debug/examples/boot_gc_generation build/fstools/bin/`. This checks boot across the allocator-GC threshold; no-write and subsequent reclamation invariants belong in deterministic filesystem simulation. The bootloader consumes the recipe-patched RedoxFS source, not a separate registry version; after changing it, cook `redoxfs`, `bootloader` and `base`, then rebuild the image so its EFI partition contains the new bootloader.

RedoxFS's deterministic simulation runs with `sim/redoxfs/run.sh SEEDS OPS`, for example `sim/redoxfs/run.sh 1000 10000`. It is a host crate with its own `Cargo.lock` that builds against `recipes/core/redoxfs/source`, so fetch that recipe first (`make f.redoxfs`); in a folder whose source is being edited, run it in a lane worktree. Each seed formats a simulated disk and runs a seeded workload of creates, writes, truncates, renames, links, unlinks, directory changes, fsyncs, time changes, key-slot changes and reformats against RedoxFS's transaction layer and an in-memory model. It also injects read errors and power losses at write boundaries, either on a disk that writes in order or on one with a volatile cache that drops, keeps, reorders or tears unflushed writes. After every operation and every crash it checks that the volume mounts, that it matches the model (contents, entries, links, directory times), that no block is both free and used or neither, that the allocator log rebuilds the running free set, and that a read-only mount writes nothing. `sim/redoxfs/regressions.txt` lists seeds that run first. A failure prints its seed and a shrunk replay, which `sim/redoxfs/run.sh replay FILE` runs again.

`sim/redoxfs/run.sh maps SEEDS OPS` runs a second seeded workload against RedoxFS's page cache (`src/page_cache.rs`), whose pages back every shared mapping of a file. It creates, opens, closes and unlinks files, so that new files reuse freed nodes, writes, reads and truncates through handles, maps ranges shared, writes through them, unmaps and fsyncs, and sends maps and unmaps of no bytes or off a page boundary, which must answer `EINVAL`. One write, truncate or `O_TRUNC` open in eight has a disk write fail during its commit; it must fail and change nothing. After every operation it checks every mapped byte, read and size against a model, and that the cache holds no node without a handle; once everything is closed, every file on the disk must match the model.

`sim/redoxfs/run.sh SEEDS OPS --flush-on-unmount` runs the same workloads the way host image builds mount a volume (`redoxfs --flush-on-unmount`, which `mk/disk.mk` and `scripts/boot-signing-lib.sh` pass): commits do not flush, the disk has a volatile cache, and there are no power losses. Between remounts it checks the live volume against the model; after each clean unmount (cleanup, then one flush) and at the end, the state on the disk must match the model. Replays of this mode start with `seed N flush-on-unmount`. The regression seeds always run with per-commit flushes.

`ferrion-run`'s storage scopes are checked with `python3 scripts/vm-test.py agent-scope agent-clone agent-scope-overhead --timeout 300` on the x86_64 desktop image; the docstrings of those tests in `scripts/vm-test.py` say what each route and step checks. Neither `ferrion-scope` nor `ferrion-run` has a `[source]`, so after editing a crate `make r.<recipe>` reports `cached`: cook them with `make cr.<recipe>`. The proxy's path resolution has a deterministic simulation, `sim/ferrion-scope/run.sh SEEDS STEPS`, a host crate that builds against `recipes/core/ferrion-scope/crate`: each seed builds a tree of folders, files and symlinks and a scope of read-write, read-only and aliased grants with hidden folders, then resolves random paths from current and stale starting folders while the tree is renamed and changed inside the read-write grants, and compares every answer with a walk of the folder view the scope describes. The seeds in `sim/ferrion-scope/regressions.txt` run first.

The x86_64 desktop's command and name-resolution regressions run with `python3 scripts/vm-test.py cli-tools resolver --arch x86_64 --config desktop --timeout 120`. `cli-tools` checks GNU sed, GNU awk and extrautils' gzip tar round-trip with `-C`; it does not cover process arguments. `resolver` checks hosts-file names as an ordinary user and captures DHCP and DNS packets to compare the queried server with the advertised server. Both need an image rebuilt with the recipe patches; installing a new libc alone does not update programs that linked it statically.

The package commands run with `python3 scripts/vm-test.py ferrion-cli update-today --arch x86_64 --config desktop --timeout 120`. `ferrion-cli` reaches no outside server: it checks that `ferrion search` refuses with exit code 6 while the image names no package source, then adds a source served from the host for the check, holding one package of this build's `repo/` (`gnu-make`, which the desktop image lacks) signed by the build's key, and installs, runs and removes it; `gnu-make` must be cooked. `update-today` runs `ferrion update` and `pkg update` as root with the network up and passes when nothing was fetched: no TCP connection or DNS question in a capture of `net0`, the hashes of `usr/lib/boot/kernel` and `usr/lib/boot/initfs` unchanged, and the next start reaching the login. That a replaced kernel or initfs is refused at the next start is `scripts/secure-boot-test.sh`'s tamper cases.

Signed update index verification is checked by deterministic simulation with `sim/ferrion-update/run.sh SEEDS STEPS`, for example `sim/ferrion-update/run.sh 500 200`, and inside the guest with `python3 scripts/vm-test.py update-index --arch x86_64 --config desktop --timeout 120`. Both drive `ferrion-update` across the eight UP1 cases (wrong signing key, replayed older serial, channel downgrade below installed release, snapshot index hash mismatch, object byte flip, object exceeding stated size, unknown key or format, and a valid root file older than `fresh_days` accepted with a notice and replaced by a newer one) and require the installed state to stay unchanged after every refusal. `update-index` builds real signed snapshots from `repo/` with `target/release/ferrion-release`, serves them from the host to `update-index-probe` in the guest, checks that every request sends the fixed user-agent with no query or cookie, and checks that `ferrion update` still exits 6 until UP3.

The GTK display check is `python3 scripts/vm-test.py gtk-window --config firefox-window --timeout 120`, after building `config/x86_64/firefox-window.toml` in a lane worktree. It uses the already cooked Firefox package and adds `gtk-window-probe`: a native GTK3 window with a fixed blue background and white label, closed by a timer. The check logs in graphically, starts the probe from the serial shell with `GDK_BACKEND=orbital ORBITAL_DISPLAY=/scheme/orbital`, checks the screenshot's background and label pixels, then requires a normal exit and removal of the window. It saves `gtk-window.png`, `gtk-window-closed.png`, pixel counts and the serial log under the run directory. This proves GTK's Orbital backend, not Firefox's display support: Firefox's `cairo-gtk3-wayland-only` toolkit rejects an Orbital GDK display and needs a running Wayland compositor.

The CJK regression is `python3 scripts/vm-test.py firefox-cjk --config firefox --timeout 120 --make QEMU_MEM=4096`, after `make r.noto-sans-cjk` and rebuilding the image. This check additionally needs host Pillow with FreeType variable-font support and `fc-scan`. It renders a local canvas page with Chinese (Simplified, Traditional and Hong Kong), Japanese and Korean, using the guest's generic sans-serif font and each canvas's language. Every glyph's dark-pixel mask must overlap an independent host FreeType rendering of the same pinned OTC at weight 400 by at least 70 percent intersection-over-union, allowing only a two-pixel translation for rasterizer alignment. Empty boxes, absent text and wrong glyph shapes therefore fail individually, rather than passing because the PNG is nonblank. The run saves `cjk.png`, `cjk-reference.png`, per-glyph scores and guest `fc-match` results, which must select SC, TC, HK, JP and KR respectively. `boot`, `shells` and the separate `firefox-headless` local/HTTPS cases remain the regression checks.

The corresponding Wayland check is `python3 scripts/vm-test.py gtk-window-wayland --config firefox-wayland --timeout 120`. That config derives from `wayland.toml`, runs cosmic-comp nested inside Orbital, and records the compositor's actual `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR` in `/tmp/gtk-window-session`. The check logs in as root to match this development compositor session, sources that environment and runs the same probe with `GDK_BACKEND=wayland`. To try Firefox on that display, source the same file from Bash, create `/tmp/firefox-window-profile`, then run `GDK_BACKEND=wayland MOZ_ENABLE_WAYLAND=1 firefox --no-remote --profile /tmp/firefox-window-profile about:blank` without `MOZ_HEADLESS`. GTK prefers Orbital when `ORBITAL_DISPLAY` is inherited, so selecting its Wayland backend explicitly matters even though Firefox itself is a Wayland-only build. The GTK probe does not prove that Firefox finishes startup or renders a page; `python3 scripts/vm-test.py firefox-window --config firefox-wayland --timeout 180 --make QEMU_MEM=4096` does: it opens Firefox on a local page, types a second local address and https://example.com/ into its address bar, and records first paint, load times and the guest memory in use before and with Firefox.

The GPU host reference runs with `nice -n 10 python3 scripts/gpu-reference-guest.py --vk-driver /usr/share/vulkan/icd.d/intel_icd.json --render-node /dev/dri/renderD128` (choose the host's actual ICD and render node; `VK_DRIVER_FILES` also supplies the ICD). It needs Python 3.11+, `bsdtar`, `zstd`, x86_64 Linux with accessible KVM, QEMU with Venus and `egl-headless`, and working host graphics drivers. It needs no FerrionOS build or host root: checksum-pinned Fedora RPMs become an initramfs, whose programs execute only inside an offline, windowless QEMU guest with `-snapshot`. The host reads archive data without running package scriptlets. First use downloads exact signed builds from Fedora's Koji archive; `--fetch-only` populates the cache, and subsequent runs check every cached hash. The script carries the build paths, SHA-256 values and release-key fingerprints used to authenticate the RPM headers and payloads when establishing the pins. `vulkaninfo`, `eglinfo`, and the host package manager add runtime and package versions when installed; an unusable host or a driver mismatch is `BLOCKED` (exit 2).

The default variant is `fedora45`, containing Fedora 45 release and updates packages. `--variant mesa263` selects the same base with rawhide Mesa matching the target release and its minimal runtime dependencies; `--variant all` writes both in one record. Both retain Fedora 45's kernel. The record labels Mesa, glibc and LLVM versions and lists every input hash. Each invocation boots the three device lines twice by default and compares scene hashes, differing-pixel counts, and the complete Venus capset bytes. It writes one `build/gpu-reference/run-*/result.json`, with per-boot serial logs and `virtio_gpu_*` QEMU traces beside it. For a capset comparison, select the matching variant and the same host GPU and QEMU device line, then read `variants[].runs[].guest.venus_capset` (`bytes_hex`, byte count and SHA-256).

`PASS` checks virgl, the CPU reference, Zink on Venus, and host submission evidence. Native contexts are recorded separately and do not gate this Venus reference: the stock Fedora packages leave Mesa's `intel-virtio-experimental` option at its default `false`, so capset 6 can be offered by the host while the guest's Intel native driver remains unavailable. The record preserves the native Vulkan and OpenGL attempts and links the package-build evidence. This is a Linux reference for the host, not proof of FerrionOS GPU support.

Mapping evidence is path-based, not vendor-based. Every Venus boot additionally creates a host-visible DRM blob, maps it twice, writes two byte patterns through opposite mappings and checks the other mapping byte for byte. The record stores the resource ID, byte count, passes and mismatches under `guest.mapped_blob`. Host submission and blob-create traces remain mandatory. A mapping is evidenced either by `virtio_gpu_cmd_res_map_blob` or by the successful guest round-trip matched to that resource's ID and size in the host's blob-create trace; `trace.mapping_evidence` names the route. [QEMU v11.1.3's `virtio_gpu_virgl_map_resource_blob`](https://github.com/qemu/qemu/blob/v11.1.3/hw/display/virtio-gpu-virgl.c) returns before its map trace event when `virgl_renderer_resource_map_fixed` succeeds, so a missing event alone is not a failed mapping. Exact rendered pixels, non-CPU renderer checks and repeated capset comparisons remain required.

For the FerrionOS desktop image with the `config/x86_64/mesa-cpu.toml` probe overlay, `scripts/vm-test.py vk-exact` checks the same frame through Venus; `scripts/vm-test.py gl-exact --venus` checks it through Zink on Venus. Both accept `--repeat 3`. The selected Vulkan device's `GPU_VK` line includes its API version, Mesa version and device-extension count. To select a different host GPU without changing the default, pass both `--make QEMU_RENDER_NODE=<that GPU's render node under /dev/dri>` and `--make QEMU_VK_DRIVER_FILES=<its driver's ICD file under /usr/share/vulkan/icd.d>`. These existing make options control QEMU, not the guest's ICD. The harness selects `egl-headless`; `mk/qemu.mk` adds `honor-guest-pat=on` to KVM for Venus on an Intel processor.

`scripts/vm-test.py audio-apps` exercises the audio service through its public scheme and the Rust client in `recipes/core/ferrion-audio/crate`: legacy PCM playback, two program identities with independent gains, readable `volume`, the CLI's JSON commands, and 10,000 stream opens and closes. It boots with its own HDA device and WAV backend, as `audio-baseline` and `audio-ring` do. The first boot uses the old PCM interface too, so a missing probe is not accepted as the expected red result. Build `audio-probe`, `ferrion-audiod` and `ferrion-cli` before the green run.

`scripts/vm-test.py audio-snoop --config audio-snoop` checks that hearing is refused by default, on the image of `config/x86_64/audio-snoop.toml`. Only that test config writes `/etc/ferrion-audiod/test.conf`, which gives the server a loopback input fed through `/scheme/audio/loopback` and a microphone grant for factories in the session `serial-console`. As root on the serial console, 440 Hz plays into the loopback input and a program `tone-c` plays 880 Hz. A record stream without a grant must read zeros and exit 0, one with the test grant must hear 440 Hz (zero crossings within 2 percent of 880 a second) and no 880 Hz, and a tap on `tone-c` must hear it only while a grant from the capture service's handle (`/scheme/audio/grants`, held by `audio-probe grant`) names it. It boots with the same HDA device and WAV backend as the other audio checks.

The AU2 stream interface is stereo float32 little-endian at 44,100 Hz, opened at `/scheme/audio/stream`; the scheme root remains signed 16-bit stereo at the same rate. A stream's relative `gain` handle takes amplitude decibels, or `mute`. Root can create `/scheme/audio/factory/<identity>/<session>` and pass its descriptor to a client, which opens `stream` relative to it: the identity is attached to that factory, not supplied by the client. Until launchers pass factories, named stream opens use the kernel caller's process ID and user ID, not a claimed executable identity. Root-only `program/<identity>/gain`, `session/<session>/gain`, `apps`, `status` and `stats` expose controls and diagnostics. Program and session gains persist in the running server, not across restarts. The existing `volume` handle remains available to existing clients, with its original 0–100 cube law. Capture, shared client rings and the launcher integration are not part of this interface yet.

`ferrion audio status`, `apps` and `volume` each accept `--json`. `volume --app ID 50 --yes` sets half linear amplitude for that program; `volume 50 --yes` retains the legacy master curve. The service starts in place of `audiod` through the config's replacement `20_audiod.service`, serves the same `audio` scheme and retains only `memory` and `rand` in its namespace after opening the output device.

The first reference baseline used Debian 13: Mesa 25.0.7 reported Venus API 1.3.269, conformance 1.3.0.0 and 113 Intel device extensions; a Mesa 26.2.6 overlay reported API 1.4.334, conformance 1.4.0.0 and 178 extensions. Both produced scene hash `47972063c7a47bfb` with zero differing pixels and the same 160-byte Venus capset SHA-256, `11069f17d3858d6b725a3b2b2b810fafc6ae6529ccdedf45bab62acdcb342609`. Its kernel 6.12 could not use Intel native contexts. These are historical host-specific measurements, not expected capability counts for every host. The reference now uses Fedora; the separate Linux compatibility layer's Debian pin is unchanged.

FerrionOS's own side of that device is checked with `python3 scripts/vm-test.py gpu-context --repeat 10 --timeout 120` on the x86_64 desktop image. It boots with `gpu=venus`, so it answers `BLOCKED` on a host that cannot, and runs `gpu-probe-context` as root, which opens render handles on `/scheme/gpu.virtio-gpu` and creates a Venus context on each through the DRM requests Venus makes. It compares the Venus capset's sha256 with the newest record of `scripts/gpu-reference-guest.py` under `build/gpu-reference/`, or with the value above when there is none, and reads QEMU's trace for the acknowledged virgl feature and each context's creation and destruction; the script's header says what passes. It proves a context on the host, not that anything is drawn.

The driver host's link is checked with `python3 scripts/lxhost-link.py` (ADR 0046, slice L1a), a host check with no VM. It cooks the recipe `ferrion-hardware` from scratch (`make cr.ferrion-hardware`, so it needs the container or the native tools and the prefix, and network for the fetch) and reads the link census the build leaves in the recipe's `target/<target>/build/census/`: every symbol Linux's files need, and whether relibc, the shim or the shim's refusal table provides it. It passes when no symbol is unresolved and every refusal names a symbol Linux's files need. A refused interface ends the host with its name when it is called, so a green link proves no behavior. `--no-cook` rereads the last census; the cook's log is `build/lxhost-link/cook.log`.

`python3 scripts/vm-test.py desktop-columns --config wm-columns --repeat 10` checks the native ferrion-wm session at 1280 by 800. Three separate Wayland clients match the window regions of the columns fixture, then ordinary compositor IPC floats and positions them to match the traditional fixture. Both cases run with corners off and on. The terminal client deliberately draws slowly. Each run saves the screenshots and individual input, client-presentation and cursor timings in `result.json`; median 16.7 ms and 99th percentile 33 ms are recorded conditions, not functional pass requirements. Presentation means synchronous display handoff, not scanout. [ADR0036](adr/0036-native-window-compositor.md) records the backend, measurement and test-session choices. `python3 scripts/ferrion-wm-config.py --check` checks that the installed KDL files match their fixture-derived generator.

For timing evidence on a shared host, run `python3 scripts/vm-test.py desktop-columns-timing --config wm-columns --repeat 10 --host-load-limit 12 --host-load-wait 600 --timing-budget 1800`. The limit is half the CPUs by default. It waits before each boot, records uptime and load at boot, samples every ten seconds and checks each case's final load. A boot that exceeds the limit keeps its functional verdict and all measurements as `HOST_LIMITED`, then another is tried. Only eligible boots count toward `--repeat`. The per-boot wait and total budget bound collection; exhaustion returns `BLOCKED` and exit 2 rather than a compositor timing verdict.

`python3 scripts/vm-test.py shm-reuse --config shm-reuse` compares ordinary file writes and shared-map writes with reads through a second shared mapping. It repeats creation, mapping, unmapping and unlinking with different patterns and sizes, including cases that retain an older mapping. The standalone probe exits unsuccessfully on any byte mismatch. The layout client's mapped buffer pool does not remove this independent OS check.

## What upstream's CI ran

Upstream gates its merge requests on a `.gitlab-ci.yml` that is not part of this checkout, and FerrionOS has no CI of its own yet. The upstream jobs, read on 2026-11-20:

- `cargo fmt -- --check`
- `RUSTFLAGS="-Dwarnings" cargo test --locked`
- `make CONFIG_NAME=ci SKIP_CHECK_TOOLS=1 repo-tree ARCH=<arch>` and the same for `CONFIG_NAME=demo`, with `PODMAN_BUILD=0`, for each supported architecture: `x86_64`, `aarch64` and `riscv64gc`
- `./scripts/fetch-changed.sh`, which fetches every recipe whose `recipe.toml` differs from `origin/master` and so needs a git checkout
- `make desktop` with `REPO_BINARY=1` and `FSTOOLS_NO_MOUNT=1`, an image assembled from prebuilt packages. Here that job also needs `VERIFIED_BOOT=0`: verified-boot signing mounts the image through FUSE, which `FSTOOLS_NO_MOUNT=1` leaves out
